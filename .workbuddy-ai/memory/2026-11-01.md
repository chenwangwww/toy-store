## 修复 Prisma 迁移漂移（Drift detected）

- 现象：`prisma migrate dev --name add_email_code` 报 Drift，要求 reset。`migrate status` 却显示 up to date（它只比对 `_prisma_migrations`，不做结构对比）。
- 根因：`bannedAt` / `bannedReason` / `RefreshToken` 表当初用 `prisma db push` 推库，从未生成迁移文件；迁移历史只有 `init` + `add_is_admin`。
- 处理（保留数据，不 reset）：
  1. 备份 `prisma/dev.db` → `dev.db.bak-20261101`
  2. `prisma migrate diff --from-migrations ... --to-schema-datasource ... --shadow-database-url` 生成差异 SQL
  3. 落成 `20261101060000_sync_banned_and_refresh_token`，`migrate resolve --applied`（不执行）
  4. `migrate dev --name add_email_code` → 生成 `20261101070006_add_email_code`
- 两个陷阱（已写进文档 3.3）：
  - 必须先跑 diff 再 mkdir 迁移目录，否则空目录被算进 `--from-migrations`，diff 为空。
  - 影子库路径要每次换新，Prisma 不自动清空，复用会报 table already exists。
- 迁移命名顺序：Prisma 按文件夹名字典序执行，手工命名的基线时间戳要小于 feature 迁移，否则新库上顺序颠倒（本次已把基线从 `110000` 改名 `060000`，并同步 UPDATE `_prisma_migrations.migration_name`）。
- 验证：`migrate status` 正常；`migrate diff --from-migrations --to-schema-datamodel` 返回空迁移（证明历史能精确重建 schema）；数据完好 3 用户/5 商品/0 订单；EmailCode 增删测试通过。
- 文档已补 3.2（改用 `cd apps/api && npx` 而非 `pnpm --filter exec`）+ 3.3（漂移处置全流程）。
- 遗留：`apps/api/prisma/dev.db.bak-20261101` 是备份，确认无误后可删（未加 gitignore，注意别误提交）。
